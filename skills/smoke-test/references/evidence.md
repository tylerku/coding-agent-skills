# Runtime and Screenshot Evidence

Evidence must let another person understand what was exercised, what appeared after each action, and where the run stopped.

Record the selected depth, feature surface, challenge hypothesis, and evidence channels before execution. A passing screenshot cannot substitute for a required database, provider, webhook, job, or recovery observation.

## Checkpoints

Capture one screenshot after each meaningful state transition, including:

- the established entry or start state;
- each step whose result is necessary for the next action;
- confirmation, validation, loading-complete, empty, error, or permission state material to the journey;
- the final expected outcome;
- the exact failure state when a step fails.

Do not take several indistinguishable screenshots of incidental clicks or transient animation frames. A "step" in the report is an observable checkpoint, not every pointer movement or keystroke.

Use stable filenames such as:

```text
<journey-order>-<journey-id>/<viewport>/<step-order>-<checkpoint>.png
```

## Assertions

Each screenshot entry must include:

- the action performed;
- the expected state;
- the observed state;
- the assertion result;
- the artifact path or URL;
- relevant console or network evidence, if any.

Each edge or failure case must additionally include the surface category, the defect hypothesis it tried to expose, how the condition was established, and the observed recovery or containment behavior.

Prefer assertions on accessible names, visible text, URL, enabled state, persisted state, or API response. A screenshot without an assertion is illustrative, not proof.

## Data safety

- Use test identities and synthetic data.
- Avoid capturing secrets, tokens, payment details, private messages, or unrelated personal information.
- Redact before publication when safe recapture is impossible, and disclose that the image was redacted.
- Do not publish an image to a public host unless the project explicitly authorizes that host and the image is safe for public access.
- Keep screenshots out of source control unless the project explicitly treats test fixtures or baselines as source artifacts. Proof generated by this skill is not a fixture by default.

## Runtime failures

Record unexpected console errors and failed application requests with their source, status, and relevance. Ignore browser-extension noise and known unrelated baseline failures only when there is concrete evidence for the classification.

Use finite waits tied to observable conditions. On a suspected transient failure, allow one diagnostic retry and label it. If the retry passes, report the initial failure and the successful retry; do not erase flakiness from the evidence.

## Environment receipt

Record enough context to reproduce the run without exposing credentials:

- exact commit SHA;
- clean or dirty worktree state and changed-file inventory when dirty;
- UTC timestamp;
- environment and base URL classification;
- server provenance tying the running application to the tested checkout and state;
- browser and viewport;
- journey actor role;
- relevant feature-flag or test-data profile names;
- selected depth and the reason it was selected;
- applicable surface categories and challenge-case inventory;
- runner or test harness;
- artifact storage location and access classification.
